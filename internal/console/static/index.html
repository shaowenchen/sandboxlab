Using Sandboxes

What this is

Sandboxes are disposable Kubernetes environments created from a template. A sandbox is a namespace of its own, reached at an address the console and the CLI print, and deleted when its lifetime runs out or when you delete it. The whole thing runs on a throwaway cluster, so nothing is left behind.

Create one

From the console, open Sandboxes and press New sandbox, then choose a template. Or from the CLI: 


    

      A create returns as soon as the objects exist; the container is pulled
      after that, and the list shows a sandbox still starting as
      Pending until it is up.
    


    
Reach it

    

      A template with a port gives the sandbox a URL — the aio
      address on the agent-infra template opens a desktop in a browser.
      A template with no port serves no URL; it is a workspace you run things in.
      Either way, two primitives reach inside:
    

    

    

      exec runs one command and waits — its exit status is the
      command's own. cp moves a file in whichever direction the side
      naming a sandbox says, and - means stdin or stdout. This is
      also how an agent reaches a sandbox: the same two over HTTP at
      POST /api/v1/sandboxes/{id}/exec and
      GET|PUT /api/v1/sandboxes/{id}/files.
    


    
Templates

    

      A template says what image to run, what ports it serves, and how long a
      sandbox may live. Three ship compiled in — agent-infra (a browser,
      shell, filesystem, MCP server and VS Code), agent-sandbox (a small
      command-execution runtime) and opensandbox (a polyglot
      Python/Java/Go/Node workspace). These are built-in and cannot be
      removed. More can be added to the running control plane from the
      Templates tab, with sandbox catalog add, or with
      POST /api/v1/catalog; an added one appears under an
      Added list and can be removed. Additions are held in memory and are
      not persisted: they are forgotten when the control plane restarts, and the
      built-ins are what it comes back to.
    


    
The API

    

      The console is a client of the same HTTP API the CLI uses. It is described
      at /api/v1/describe, and every call
      carries the key in Authorization: Bearer <key> or
      X-Sandbox-Key. The data-plane addresses under
      /sandbox/ also take ?key=, because a browser
      navigation cannot set a header.
    

    


    
When it is not working

    
    
      
  • A Failed sandbox has a message —
          hover the state to read it.
    • 
      
  • Logs on a row shows the tail of the container's output, which
          is where a command that exited non-zero leaves its error.
    • 
      
  • A sandbox that cannot pull its image stays
          Pending: the
          agent-sandbox template ships no image, so its
          image must be built and pushed first.
